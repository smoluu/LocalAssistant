# LocalAssistant - AI Agent Guide

## Project Overview

LocalAssistant is a local-first Android voice assistant application that runs entirely on-device or connects to local network endpoints for LLM, STT (speech-to-text), and TTS (text-to-speech) inference. The app provides a continuous listening mode via a foreground service with VAD-based voice activity detection, streaming chat responses through Jetpack Compose UI, and real-time TTS audio playback using AudioTrack.

All AI model endpoints are configurable at runtime - the app connects to local services such as Ollama (LLM/STT) and Piper or Coqui (TTS). It supports streaming LLM responses via SSE, wake word detection through a separate foreground service, and includes features like conversation summarization, message pinning, settings presets, and Gruvbox-themed Material3 UI.

## Local Development Setup

Machine-specific facts (the developer's local endpoints, adb device, build/deploy commands) live in `AGENTS.local.md`, which is **git-ignored** and not part of the project. Read it when working on that machine; never commit it, and keep it out of this file's general documentation.

## Tech Stack
- **Language**: Kotlin 1.9+, JVM target 17
- **UI**: Jetpack Compose (Material3) with Navigation Compose
- **Architecture**: MVVM - AndroidViewModel + StateFlow for reactive state
- **Database**: Room (ChatMessageEntity, single table `chat_messages`)
- **Networking**: OkHttp with SSE streaming support for LLM and TTS endpoints
- **Serialization**: kotlinx.serialization (@Serializable on ChatMessage), org.json for API responses
- **Persistence**: SharedPreferences (not DataStore - despite build.gradle comment mentioning DataStore)
- **Audio**: AudioRecord for capture, AudioTrack for playback (no MediaRecorder in production code)
- **Min SDK**: API 35 (Android 14)
- **Target SDK**: API 35

## Architecture & Key Directories
- `domain/model/` - Data classes: `ChatMessage`, `MessageRole` enum, `AppSettings` data class with all config fields
- `data/local/` - Room database: `LocalAssistantDatabase` singleton, `ChatMessageEntity` + `ChatMessageDao` interface
- `data/remote/` - `ApiClient` object with static methods for chatCompletion (SSE streaming), transcribeAudio, synthesizeSpeech, fetchModels, fetchVoices
- `data/settings/` - `SettingsRepository` using SharedPreferences with custom JSON preset serialization (no kotlinx.serialization for presets)
- `service/` - `VoiceAssistantService` (foreground service with full pipeline: audio capture → VAD → STT → LLM → TTS), `WakeChatService` (the hands-free wake-word pipeline as a microphone foreground service, so it keeps running while the app is minimized; its persistent notification carries the reply and reopens the app). `WakeChatService` **is** an `android.service.voice.VoiceInteractionService`, so a platform that hosts hands-free conversations can instantiate it as its own voice service (see the VoiceInteractionService gotcha below for the exact hooks and manifest registration). Its drawing half is `WakeChatSessionService`, an `android.service.voice.VoiceInteractionSessionService` in the same package: `onNewSession(Bundle)` returns a `VoiceInteractionSession` that the system composes into a window of type `TYPE_VOICE_INTERACTION` over the home screen or whatever app the device is showing - the only rendering that exists while the app is minimized (see the session gotcha below).
- `ui/chat/` - `ChatViewModel` + `ChatScreen` (single conversation history; the old QuickChat pair was removed when quick chat became the wake-word service)
- `ui/wake/` - `WakeChatViewModel` + `WakeChatScreen`: the overlay UI only - the pipeline itself lives in `service/WakeChatService`. The ViewModel is a thin renderer: it forwards the service's companion `StateFlow`s (`messages`/`overlay`/`phase`/`statusMessage`) and sends the start/stop intents, so `WakeChatScreen` never has to know a service is running. It is an **app-level overlay**, not part of the chat screen: `MainActivity` draws a `WakeOverlay` composable *after* `MainNavigation` inside the same `Surface`, so the card appears over chat, settings or the home view. The `overlay` StateFlow is true only during an exchange, and the whole card column sits inside `AnimatedVisibility` + `slideInVertically` - while the app is merely listening nothing is painted.
- `ui/settings/` - `SettingsViewModel` with preset management, model fetching, wake-word enrollment/testing and the wake-word chat's own section (reply window, chat close timeout, a manual "Trigger An Exchange" debug intent), `SettingsScreen`
- `ui/common/` - `CommonUtilities.kt`: audio recording helpers (`recordAudioWithVAD` returns `null` when no speech was heard and trims the clip to the utterance), WAV conversion, TTS playback, text splitting, chat export. `WakeWordDetector.kt`: the on-device wake-word matcher - `extractWakeFeatures`/`mfcc` (10 ms MFCC features, 40 ms frames, radix-2 FFT; `mfcc` prepares every clip with `prepareSignal` = low-pass + gain normalise, and `extractWakeFeatures` gates clips with `containsSpeech`), `bestMatchCost` (DTW against enrolled references), `wakeCostThreshold(sensitivity, references)` (relative to `referenceSpread`), `referenceFrameCount` with `MAX_REFERENCE_FRAMES`/`MAX_REFERENCE_SECONDS`, and `loadWakeReferences`/`saveWakeReference`/`clearWakeReferences` persisting references in `<filesDir>/wake_references.txt`. `DefaultAssistant.kt`: the platform's default-assistant state and the page that sets it — `isDefaultAssistantHeld(Context): Boolean?` (null = the platform has no assistant role, never render that as "not set") and `assistantSettingsIntents(Context): List<Intent>` (the role request when the role API exists, otherwise the two documented settings activity keys in priority order)
- `ui/theme/` - `Theme.kt`: Gruvbox dark/light color schemes (Material3)
- `receiver/` - `AppBootReceiver` (restarts service on boot), `NetworkStateReceiver` (restarts on network change)
- `widget/` - `VoiceAssistantWidget` (home screen widget for quick mic control)

## Coding Standards & Conventions
- Use `StateFlow` for all reactive state exposed to UI; wrap with `asStateFlow()` if mutable internally
- All ViewModels extend `AndroidViewModel`; use `viewModelScope` for coroutines
- Audio recording uses 16kHz mono 16-bit PCM (`ENCODING_PCM_16BIT`, `CHANNEL_IN_MONO`)
- WAV headers are written manually with little-endian byte order - use `writeIntLE`/`writeShortLE` helpers from CommonUtilities
- TTS playback uses AudioTrack with sample rate fallback: `[16000, 22050, 24000, 8000]` (or `[16000, 22050, 24000, 44100, 8000, 11025, 8000]` in VoiceAssistantService)
- API calls always run on `Dispatchers.IO` wrapped in `withContext()` or use OkHttp's built-in IO scheduling
- Settings are loaded fresh from SharedPreferences before each service operation (not cached indefinitely)
- Package names follow `com.localassistant.app.*` convention

## Important Patterns & Idioms
- **MessageFlow**: Messages stored as `StateFlow<List<ChatMessage>>` in ViewModels; no Room sync is currently implemented (entities exist but DAO is not wired to ViewModels)
- **Streaming**: `ApiClient.chatCompletion()` uses SSE with callback pattern - `onChunk: (String) -> Unit` receives each delta; full response accumulated and finalized after `[DONE]` marker
- **Reasoning extraction**: Streaming chunks use `\u0001` separator for reasoning content; final response parsed via `parseReasoningAndContent()` supporting `<think>`, `<reasoning>`, `<thinking>` tags and OpenAI format with `reasoning_content` field
- **TTS Playback**: AudioTrack with sample rate fallback loop - tries each rate until one succeeds; no completion listeners (unreliable on some devices)
- **Audio Recording**: PCM via AudioRecord, manually converted to WAV with proper RIFF headers in VoiceAssistantService and CommonUtilities
- **Retry pattern**: `executeWithRetry(operationName, maxRetries=3, delayMs=1000)` wraps API calls in VoiceAssistantService

## Things the Agent Should NEVER Do
- Never hardcode API endpoints - always use values from `AppSettings` loaded via `SettingsRepository`
- Never make blocking network calls on main thread - all OkHttp calls must be in coroutines with `Dispatchers.IO`
- Never add an external wake-word runtime (Porcupine/Snowboy/rustpotter as a native library) without checking licence and on-device footprint - this Kotlin toolchain has **no C FFI**: `android.util.CLibrary` and `@JNI` are both unresolved, so a Rust `.so` cannot be loaded. The wake matcher is a pure-Kotlin port of rustpotter's References mode in `ui/common/WakeWordDetector.kt`
- Never trigger the wake word from the STT transcript - the trigger must be on-device (`WakeWordDetector`); STT may only transcribe the request after the phrase has matched
- Never remove foreground service notifications - they are required by Android API 35+ and declared in AndroidManifest.xml
- Never commit API keys or base URLs that contain credentials to version control
- Never use `kotlinx.serialization` for preset JSON - the project uses manual string building/parsing (see SettingsRepository preset methods)

## Gotchas & Non-Obvious Knowledge
- **Min SDK is 35**: Not 26 - the build.gradle.kts explicitly sets `minSdk = 35`. Do not use API 34+ deprecation warnings as guidance for compatibility.
- **TTS 0-byte bug**: The proxy API (Piper) returns empty responses if `response_format` is not set to `"wav"` in TTS requests - always include this parameter when modifying TTS endpoints
- **MediaPlayer looping**: Never rely on completion listeners; always calculate duration and wait explicitly for audio playback
- **Streaming state cleanup**: `_streamingContent.value = ""` must be called AFTER adding the final assistant message, not before (see ChatViewModel.sendMessage)
- **QuickChat vs Main Chat**: QuickChat was retired when the wake-word service became its own ViewModel. The wake chat keeps its own `_messages` StateFlow, independent from the main conversation history.
- **Wake word needs enrollment**: `WakeWordDetector` has no built-in phrase - it matches the recorded clip against user-enrolled WAV references stored in `<filesDir>/wake_references.txt` (max 8, each ≤ `MAX_REFERENCE_FRAMES` = 500 frames, i.e. ≤ `MAX_REFERENCE_SECONDS` = 5 s). With zero references the wake service reports "No wake-word references recorded" and never fires. Settings exposes "Record Reference"/"Clear References" buttons and the recorded count, and enrollment reports the exact reason it failed ("No speech heard - say the wake phrase while recording", "No speech found in the clip", "Clip too long - keep the phrase under N seconds", "Could not save the reference") using the public `MAX_REFERENCE_FRAMES`/`MAX_REFERENCE_SECONDS`/`referenceFrameCount`.
- **Wake preprocessing is shared, never per-path**: `mfcc` starts with `prepareSignal`, a 3-tap moving average (`LOWPASS_WINDOW` = 3, keeping roughly everything below ~2.7 kHz at 16 kHz) followed by `normalizeGain` scaling the clip's loudest sample to `TARGET_PEAK` = 0.9. Enrollment and live detection both come through `mfcc`, so a reference is always comparable to the clip matched against it - never add gain or filter handling to only one of the two paths. `mfcc` then ends with `normalizePerFeature` (zero mean, unit variance), so a DTW cost is "this many standard deviations apart".
- **Wake silence must never fire**: `extractWakeFeatures` runs `containsSpeech` before any feature is built - the clip needs at least `MIN_SPEECH_FRAMES` = 3 voiced frames (≥ 35 % of the loudest frame) *and* `MIN_QUIET_FRAMES` = 2 quiet ones (≤ 12 % of it), all measured on the gain-normalised signal. Room noise is one uniform level and silence has no loud frame, so both are rejected. `recordAudioWithVAD` complements this by returning `null` when no speech was heard and trimming the clip to `[firstSpeech - 300 ms, lastSpeech + 500 ms]`, which also keeps enrollment under the frame limit. The wake loop treats a null/empty clip as "still detecting" - it never raises the overlay and never reports an error.
- **Wake threshold is relative to the user's own takes**: `wakeCostThreshold(sensitivity, references)` takes `referenceSpread` - the median pairwise DTW cost among the enrolled references - and multiplies it by `0.6 + 2.4 * (1 - sensitivity)`, so the strict end asks for better than the spread the user's own recordings already show and the lenient end accepts three times it, floored at `MIN_MATCH_THRESHOLD` = 0.5. Below two references it falls back to `SINGLE_REFERENCE_SPREAD` = 1.5 in normalised units. References enrolled before per-feature normalisation existed are normalised in `loadWakeReferences`, so old enrollment files stay usable. The Settings "Test Wake Word" action prints measured cost vs threshold so the slider can be tuned; sensitivity is a continuous `Slider` (0..1, 21 steps) in the Wake Word section, not two buttons.

- **Compose resolves to foundation 1.9.x, not 2.x**: the BOM in this project pulls `androidx.compose.foundation` 1.9.3, so APIs introduced in Compose 2.x are unresolved here - `LazyListState.animateScrollToEnd()` and `getEndOffset()` both fail to compile. The scroll API available is `animateScrollToItem(index, scrollOffset)`; bottom-align a growing item with `animateScrollToItem(index, item.size - layoutInfo.viewportSize.height)` using `LazyListLayoutInfo.visibleItemsInfo`/`viewportSize`. Check the jar in `~/.gradle/caches/modules-2/files-2.1/androidx.compose.foundation/` before assuming an API exists.
- **Gruvbox Theme**: Primary is `#F2A94C` (warm yellow), secondary is `#D75D00` (deep orange). The app defaults to dark theme. Avoid green/pink/blue colors - use Gruvbox palette throughout.
- **Base URL normalization**: ApiClient strips `/chat/completions`, `/audio/transcriptions`, `/audio/speech` suffixes from base URLs before appending the correct endpoint path
- **Generation settings are first-class**: `AppSettings` carries `llmMaxTokens` (default 1024), `llmReasoningBudgetTokens` (default 512) and `llmChatTemplateKwargs` (default empty), all three persisted by `SettingsRepository` under `llm_max_tokens` / `llm_reasoning_budget_tokens` / `llm_chat_template_kwargs` and carried through presets like every other field. `ApiClient.chatCompletion` appends `"reasoning_budget_tokens"` only when the value is > 0 and `"chat_template_kwargs"` only when the typed field parses to at least one pair, so a server without either control keeps receiving the exact body it expects. The budget must cover reasoning **and** the answer: a thinking model spends `max_tokens` on its chain of thought first, so too small a value answers with an empty message - which is why the Settings screen spells that out next to the fields. `buildChatTemplateKwargsJson` accepts the phone-friendly spelling (`key=value` per line, or comma-separated, `#` comments, values in single/double quotes ignored) and skips malformed lines rather than sending them; keys are limited to bare identifiers (`[A-Za-z_][A-Za-z0-9_.-]*`) because that is the only place stray JSON could be injected. Values are typed: `true`/`false` and numbers stay JSON literals, bare words become strings. The conversation summarizer and the LLM health probe deliberately keep their own small budgets instead of inheriting these.
- **Request bodies are hand-built JSON**: `ApiClient.buildChatRequestBody` is a StringBuilder, so optional fields (`reasoning_budget_tokens`, `chat_template_kwargs`) must be appended **before** the closing `}`. A comma after the closing brace compiles and parses as a Kotlin statement but is invalid JSON - llama.cpp answers 400 with `json.exception.parse_error.101 … unexpected ','; expected end of input`. The Settings LLM health probe sends a plain request, so "the test says ok while the chat 400s" is this class of bug, not an endpoint problem; `LlmSettingsTest.generationControlsStayInsideTheObject` is the oracle.
- **Wake chat holds one exchange, never a log**: `WakeChatService.closeChat()` clears `_messages` and is called when the user taps off the card (`ACTION_CLOSE_CHAT`), when the service stops, and when the close clock expires - the wake conversation is deliberately independent from the main chat history and must never accumulate across exchanges. An exchange's life is owned by two settings: `wakeReplySeconds` is the `noSpeechTimeoutMs` given to `recordAudioWithVAD` while recording the request (without it the mic stays open for the full 60 s cap and the user sees a card that never answers), and `wakeChatCloseSeconds` is how long the card stays up after `touchChat()` last stamped it. Stamp at every stage that is activity - each streamed LLM chunk, before speaking, and on the user's taps - and wait on the clock with `holdChatOpen()` before the notification-only end. Both are clamped `coerceIn(1, 300)`.
- **STT uses multipart/form-data**: Not JSON body - audio file is uploaded as `file` part with model as text part (standard OpenAI Whisper format)
- **Service state machine**: States are `"idle"`, `"listening"`, `"processing"`, `"speaking"`, `"error"` - used in both VoiceAssistantService and ChatViewModel
- **Battery saving mode**: Activates at <20% battery, drops sample rate to 8kHz. Restores when charging resumes.
- **VoiceInteractionService is a class, not an interface**: `android.service.voice.VoiceInteractionService` extends `android.app.Service`, so Kotlin must write `: VoiceInteractionService()` **with parentheses** ("This type has a constructor, so it must be initialized here" otherwise). The only hooks this toolchain exposes are `onReady()`, `onShutdown()`, `onLaunchVoiceAssistFromKeyguard()`, `onGetSupportedVoiceActions(Set<String>): Set<String>`, `onPrepareToShowSession(android.os.Bundle, Int)`, `onShowSessionFailed(android.os.Bundle)`, `onTimeout(Int)` and `onTimeout(Int, Int)` - the "Live Voice" callback names people assume (`onStartConversation`, `onListening`, `onHotwordDetected`, `onProgress`, `onCompletion`, `onNoMicSignal`, `onNotUnderstood`, `onFailure`, `onCancel`) all fail with "overrides nothing" and no transcription is ever handed to us, so the app's own record → wake-match → STT → LLM → TTS loop stays the working path and the hooks only gate/raise/lower/report an exchange. Registering it needs `android.permission.BIND_VOICE_INTERACTION` and an `<intent-filter><action android:name="android.service.voice.VoiceInteractionService" /></intent-filter>` inside the `<service>` block (that action is AOSP's `SERVICE_INTERFACE`). The developer page for the class is unusable (`web_fetch` returns a truncated 2.7 MB page with an invented member list) - enumerate the real surface by compiling `override fun onX() {}` probes instead. The system opens such a service *with the `SERVICE_INTERFACE` action itself*, so `onStartCommand` must treat that action as "start listening" - confirmed on this device, where `io.homeassistant.companion.android` starts `.assist.service.AssistVoiceInteractionService` with `act=android.service.voice.VoiceInteractionService`. Only one app holds that voice-interaction slot at a time and the user picks it in system settings, so until LocalAssistant is picked the app's own `com.localassistant.START_WAKE_CHAT` intent is the path that runs.
- **Drawing over the system UI is a separate service, with legacy UI**: the exchange is rendered by `android.service.voice.VoiceInteractionSessionService`, whose **only** abstract member is `onNewSession(android.os.Bundle): VoiceInteractionSession` (plus `onTimeout(Int)` / `onTimeout(Int, Int)`). `VoiceInteractionSession` ctors are `(Context)` and `(Context, Handler)`; the hooks that compile in Kotlin are `onCreate()`, `onPrepareShow(android.os.Bundle, Int)`, `onShow(android.os.Bundle?, Int)`, `onHide()`, `onDestroy()`, `onHandleScreenshot(android.graphics.Bitmap?)`, `setKeepAwake(Boolean)`, `finish()`. The card itself comes from `onCreateContentView(): android.view.View` / `setContentView(android.view.View)` — the **legacy Java UI**, so build it with `android.widget.LinearLayout(android.app.Activity())` + `android.widget.TextView(context)` (`setText`, `setTextColor(Int)`, `setBackgroundColor(Int)`, `textSize = Float`, `addView`). The spelling is `android.view.View`: the `android.compose*` packages do not exist in this toolchain at all, which is why Compose cannot be used there. AOSP calls `onPrepareShow` **before** `onCreateContentView`, so capture the text in the former and build the views in the latter. A session is a **separate service**, so never read the wake service's `StateFlow`s from it: the exchange travels in the `android.os.Bundle` handed to the concrete `VoiceInteractionService.showSession(Bundle, Int)` (throws `IllegalStateException` until `onReady()` has run, so wrap it). Bundle string access is `putString(key, value)` and `getString(key)` — `set`, `assign`, `put`, `putString`-as-`setString` are all "Unresolved reference". Manifest: `<meta-data android:name="android.voice_interaction" android:resource="@xml/voice_interaction"/>` inside the `<service>` block — `<item>` is rejected ("unexpected element `<item>` found in `<manifest><application><service>`") and a bare name is rejected ("`'voice_interaction'` is incompatible with attribute resource"), so it must be a `@xml/` reference. The referenced `res/xml/voice_interaction.xml` has the root tag `<voice-interaction-service>` (this is what AOSP's `SERVICE_META_DATA` comment documents); the child-element form that used `<my-service>`/`<session-service>` names is **invalid** — see the resource gotcha below for the attribute names the parser actually reads.
- **The Android-15 hotword path does not exist in this toolchain**: a compile probe over `android.service.voice.HotwordDetectionService`, `HotwordDetector`, `AlwaysOnHotwordDetector`, `SoftwareHotwordDetector`, `HotwordResult`, `android.media.voice.KeyphraseModelManager` and `android.hardware.soundtrigger.*` reports every one of them unresolved (the `android.service.voice` *package* resolves, only those classes are missing; `android.os.PersistableBundle`, `android.os.SharedMemory` and `android.view.contentcapture.ContentCaptureManager` do resolve). They are `@SystemApi @hide` in AOSP, i.e. absent from the public stubs, so no app built with these bindings can implement the system's own hotword enrollment. Consequence: the app can never enroll its own wake phrase into the system detector - the fixed system hotwords ("Hey Assistant" / "OK Assistant") are what triggers a selected assistant, and LocalAssistant's own MFCC/DTW matcher stays the only way its phrase can fire.
- **Both halves of the voice path need the app to be *selected* as the system assistant**: AOSP resolves `ServiceManager.getService(Context.VOICE_INTERACTION_MANAGER_SERVICE)` in `VoiceInteractionService.onReady()` and again in `VoiceInteractionSessionService.onCreate()`, and `showSession()` throws `IllegalStateException("Not available until onReady() is called")` until that resolves - which our `requestSession` catch swallows. So "nothing renders, I only hear the ping" means the app was never picked; `onReady()` logging is the proof of the pick, and the session service logging proves the rest of the chain. That resolution is **per-process**: `ServiceRegistry` only knows the services that were shared into the process it runs in, so an isolated session process — which contains nothing else — resolves the manager service as **null**, and the framework's next call, `deliverSession()`, throws `NullPointerException … 'IVoiceInteractionManagerService.deliverNewSession' on a null object reference` (proved on the tab: `Start proc …WakeChatSessionService … for service {…}` immediately followed by that stack at `deliverSession:139` / `doNewSession:128` / `executeMessage:66`, then `Showing crash dialog for package com.localassistant.app`). That is the "LocalAssistant has stopped" dialog, and it means the session half must **share the app's own process** — the one where `onReady()` already resolves the manager service — so the session `<service>` must not carry `android:isolatedProcess`.
- **What makes the app appear in the "Default digital assistant" picker** (verified against AOSP's own `VoiceInteractionServiceInfo.java`, `VoiceInteractionManagerServiceImpl.java` and `DefaultAssistPreferenceController.java`): the picker enumerates `queryIntentServices(Intent(android.service.voice.VoiceInteractionService.SERVICE_INTERFACE))` and then requires `getSupportsAssist()` **and** `getSettingsActivity()`, so both must be present in the resource. Two things gate eligibility before the picker is even reached: `VoiceInteractionServiceInfo`'s constructor rejects any service whose `ServiceInfo.permission` is not `android.permission.BIND_VOICE_INTERACTION` ("Service does not require permission android.permission.BIND_VOICE_INTERACTION") — and `ServiceInfo.permission` is the manifest **`android:permission` attribute on the `<service>` element**, proven by `Manifest.permission.BIND_HOTWORD_DETECTION_SERVICE.equals(hotwordDetectionServiceInfo.permission)` in the same file — and any parse error in the resource sets `VoiceInteractionManagerServiceImpl.mValid = false`, so `onReady()` never runs and `showSession()` always throws. A `<uses-permission android:name="android.permission.BIND_VOICE_INTERACTION"/>` is inert for this purpose: it is not a runtime permission and grants nothing; the capability lives on the service.
- **The `android.voice_interaction` resource is attribute-based, not child-element-based**: `VoiceInteractionServiceInfo` reads `R.styleable.VoiceInteractionService` attributes only — `sessionService`, `recognitionService`, `settingsActivity`, `supportsAssist`, `supportsLaunchVoiceAssistFromKeyguard`, `supportsLocalInteraction`, `hotwordDetectionService`, `visualQueryDetectionService` — and the resource must literally start with `<voice-interaction-service>`. `sessionService` and `recognitionService` are **both required** ("No sessionService specified" / "No recognitionService specified"), and `sessionService` is instantiated as `new ComponentName(service.getPackageName(), mInfo.getSessionService())` — the **same package**, so the session service must be declared in this app. The `<my-service>`/`<session-service>` child names parse to nothing, which is why the whole resource was invalid.
- **`RecognitionService` cannot return a transcript in this Kotlin toolchain**: `android.speech.RecognitionService` resolves with exactly three required overrides (`onStartListening(Intent, RecognitionService.Callback)`, `onCancel(Callback)`, `onStopListening(Callback)`), while `Hypothesis` (in every spelling), the `KEY_*` constants and the `Callback` members (`onResult`/`onNoMatch`/`onAudioStart`/`onAudioEnd`/`onError`) are all unresolved. So the `recognitionService` attribute is satisfied by a hollow `WakeChatRecognitionService` that only logs — and it is deliberately **not** declared as a manifest `<service>`, because declaring it would advertise the app in the separate speech-recognition picker with a service that can never transcribe.
- **Ask the platform which assistant role is held, never guess**: `android.app.role.RoleManager` (not `android.app.RoleManager`) via `context.getSystemService(RoleManager::class.java)` answers `isRoleAvailable(RoleManager.ROLE_ASSISTANT)` / `isRoleHeld(...)`, and `createRequestRoleIntent(RoleManager.ROLE_ASSISTANT)` is the platform's own way of taking the user to the picker — AOSP's `DefaultAssistPreferenceController` builds exactly that intent (`Intent(ACTION_MANAGE_DEFAULT_APP).setPackage(controller).putExtra(Intent.EXTRA_ROLE_NAME, ROLE_ASSISTANT)`). Treat "no such role" as a third state (`Boolean?`), never as "not set": claiming the user must set something they cannot set is wrong. `android.content.Intent.Settings` — the nested class holding the `android.settings.*` constants — is unreachable from Kotlin, so the action strings are spelled out in `DefaultAssistant.kt`.
- **`android.settings.voice_input` is not a real activity key** and resolves on nothing. The keys that open the assistant page are `android.settings.VOICE_INPUT_SETTINGS` (the assistant page itself) and `android.settings.MANAGE_DEFAULT_APPS_SETTINGS` (every default-app picker); `am start -W -a <key>` is the oracle for whether a vendor build registers one. `DefaultAssistant.assistantSettingsIntents` returns the candidates in priority order and `SettingsViewModel.openAssistantSettings` launches the first that resolves.
- **aapt2 invoked directly is not an oracle for manifest attributes**: `aapt2 link --manifest` carries no built-in attribute schema and reports "attribute android:name not found" for *every* `android:*` attribute even in a plain valid `<activity>` manifest. `./gradlew assembleDebug` is the only real oracle. On-device, `cmd package dump <pkg>` is the bind oracle: a `ServiceRecord` with `act=android.service.voice.VoiceInteractionService` and `bindFromPackage:null` means the app is eligible but unbound (correct until the user picks it), while a held role shows `hasBound=true`.
- **`WakeChatService.onReady()` must call `super.onReady()` before doing anything**: AOSP's `VoiceInteractionService.onReady()` is the *only* assignment of its `mSystemService` (`ServiceManager.getService(Context.VOICE_INTERACTION_MANAGER_SERVICE)` + `Objects.requireNonNull` + `linkToDeath` + `KeyphraseEnrollmentInfo`), and `showSession()` throws `IllegalStateException("Not available until onReady() is called")` while that field is null. An override that never chains to `super` leaves the whole system-driven path dead *even on a platform that has bound this app as its assistant* — every `showSession()` threw and the `requestSession` catch swallowed it silently, which is exactly the symptom the user reported ("the chat only renders inside the app's own window"). Every other hook we override has an empty base body (`onShutdown`, `onLaunchVoiceAssistFromKeyguard`, `onPrepareToShowSession`, `onShowSessionFailed`) or returns a value we deliberately replace (`onGetSupportedVoiceActions`, whose base returns an empty set), so `onReady()` is the only one that needs chaining.
- **The session half is observable, not assumable**: `VoiceInteractionManagerServiceImpl.showSessionLocked()` creates one `VoiceInteractionSessionConnection` and, when its `mBound` is false, calls `mService.showSessionFailed(bundle)` *before* showing anything. Our `onShowSessionFailed` sets `PHASE_ERROR` and the notification text "The voice session could not be shown", which is the on-device signal that the session half refused to bind — distinct from the `showSession()` throw, which now reports "The system would not draw this exchange: …" through the notification too. Kotlin `android.util.Log` never reaches logcat in this app, so a log-only diagnosis is unreadable on the device: always surface refusals in the persistent notification.
- **A vendor picker may record the choice and grant no role** (settled on the tab): ZUI's "Default digital assistant" writes `Settings.Secure.assistant` and `Settings.Secure.voice_interaction_service` — `cmd settings list secure` shows both pointing at `com.localassistant.app/.service.WakeChatService` — while `cmd role get-role-holders assistant` is empty for every user (default, `--user 0`, `--user 10`). So `DefaultAssistant.isDefaultAssistantHeld` reports "not held" for a user who *has* set it. The platform's own test for the same question is `VoiceInteractionService.isActiveService(Context, ComponentName)`, which is unreachable from this Kotlin toolchain: `ComponentName`, `android.app.component.ComponentName`, `android.app.PackageManager`, `android.util.Settings` and `android.content.Settings` are all unresolved, and `Intent.setComponent` only accepts `ComponentName?`. The service's own `onReady()` is the other half of the truth and the only reachable one — it runs only when the platform has really bound the app.
- **The binding is reportable, and only through `onReady()`**: `DefaultAssistant.kt` carries a module-level `voiceInteractionBound` that `WakeChatService.onReady()` sets *after* `super.onReady()` returns (the base resolves the voice interaction manager or throws, so reaching the next line is the proof), and `isDefaultAssistantHeld` consults it before the role query. Never try to carry this in SharedPreferences: `android.content.SharedPreferences` stores belong to the `Context` that called `getSharedPreferences`, and the settings screen and the service are different `Context`s — a plain module value works because the foreground service runs inside the app's process.
- **The platform binds the service when the setting is *written*, not at boot and not on reinstall** (observed on the tab): the picker write produced `ActivityManager: Background started FGS: Allowed [… cmp=com.localassistant.app/.service.WakeChatService … isBindService:true]`; after a reboot with the setting intact, `SystemServiceManager` started `com.android.server.voiceinteraction.VoiceInteractionManagerService` but no `com.localassistant.app` process existed and none of the ctor's failure messages ("Voice interaction service not found", "Bad voice interaction service: …", "Failed binding to voice interaction service") appeared. `cmd settings put secure voice_interaction_service …` does not re-bind either. Consequence for every deploy: `adb install` force-stops the app (`ActivityManager: Force stopping … pkg removed`), so the user must re-select LocalAssistant in the "Default digital assistant" picker after each build before the platform path can run.
- **`cmd` services on the tab are the oracles for this whole path**: `cmd -l` lists running platform services (it shows `role`, `voiceinteraction`, `settings`, `lock_settings`, `motsettings`, `secure_element` on ZUI). `cmd role` → `get-role-holders|add-role-holder|remove-role-holder|clear-role-holders|set-bypassing-role-qualification|get-active-user-for-role|set-active-user-for-role` with `[--user USER_ID]`; `cmd voiceinteraction` → `help|show|hide|disable [true|false]|restart-detection|set-debug-hotword-logging`; `cmd settings` → `get|put|delete|reset|list [--user USER_ID|current] {system|secure|global} KEY`. `cmd voiceinteraction show` answers `SecurityException: Access denied, requires: android.permission.ACCESS_VOICE_INTERACTION_SERVICE` for adbd, so the show path cannot be exercised from the host — that is not evidence the service is dead. `cmd --help` and bare `cmd` are not usage; `cmd find`/`cmd ls` do not exist.
- **The app cannot draw over other apps itself — only the platform can**: the whole `android.window` package is absent from this Kotlin toolchain. `android.window.WindowManager`, `Frame`, `Rect`, `WindowHandle`, `WindowType` and `Window` all report "Unresolved reference" at the class-name position (the package itself resolves), so `WindowManager.openWindow(View, Frame, Intent)` — the app-level way to paint a `TYPE_APPLICATION_OVERLAY` / `SYSTEM_ALERT_WINDOW` window — cannot be written here at all. `android.view.View` does resolve, but only as the content of the platform's session. Consequence: "draw the exchange over whatever is on screen" has exactly one implementation path, the `VoiceInteractionSessionService` window the system composes; the app's own `WakeOverlay` inside `MainActivity` is app-level and can never leave the app's window. Do not reach for a Compose-based overlay or a `Surface`/`WindowManager` shim here.
- **A `VoiceInteractionSession` must be built on a NON-UI context** (settled from AOSP's own `VoiceInteractionSession.java`, `Context.java`, `ContextWrapper.java` and `Activity.java`): the ctor's first act is `mContext = createWindowContextIfNeeded(context)`, which asks the context for `context.createWindowContext(DisplayManager.getDisplay(DEFAULT_DISPLAY), WindowManager.LayoutParams.TYPE_VOICE_INTERACTION, null)` **only when `!context.isUiContext()`** — otherwise it returns the context unchanged and swallows any `RuntimeException` as `Log.w("Fail to createWindowContext, …")`. `android.app.Activity` is annotated `@UiContext` (`Activity.java` line 767, `public class Activity extends ContextThemeWrapper`), so `onNewSession()` handing over `android.app.Activity()` skipped the whole step and `ensureWindowCreated()` built a `VoiceInteractionWindow` (a `Dialog` subclass) on a surface associated with nothing — the observed symptom being "the chat only renders inside the app's own window". `android.app.Service` is the right context: `Service extends ContextWrapper extends Context`, and `ContextWrapper.isUiContext()` is `if (mBase == null) return false`, which is the case for a service. AOSP proves the same object is acceptable where a `Context` is required by passing `this` to `HandlerCaller` in `VoiceInteractionSessionService.onCreate()`. `android.app.Service` compiles as the argument of `VoiceInteractionSession(Context)`, `LinearLayout(Context)` and `TextView(Context)` here, so the session service itself (`this`) is the context to pass — never an `Activity`, and never the app's `LocalAssistantApplication` context.
- **Never override `VoiceInteractionService.onBind()`**: the base returns `mInterface.asBinder()` for the interface action `android.service.voice.VoiceInteractionService` and that binder is the IPC channel the system server uses to call `onReady()`, `onPrepareToShowSession()` and `onShowSessionFailed()` in this process. An override returning `null` for every intent leaves the system's voice interaction manager unresolved — `onReady()` is its only assignment and `showSession()` throws until it exists — so no exchange is ever drawn outside the app.
- **A failed session delivery is silent**: `VoiceInteractionSessionService.doNewSession()` destroys the session when `deliverSession(token)` returns false, and `deliverSession` only logs `Log.e(TAG, "Failed to deliver session: ")` after catching `DeadObjectException`/`RemoteException`. AOSP carries `// TODO(b/178777121): Add an onError() method to let the application know what happened.` on that very method, so `onShowSessionFailed()` is **not** called for a delivery failure and nothing in our app can observe it. Read "showSession() returned but nothing painted" as a possible delivery failure, never as a success.
- **`VoiceInteractionSessionService` needs no manifest `<intent-filter>`**: the class has no `SERVICE_INTERFACE` constant and its `onBind()` returns `mInterface.asBinder()` unconditionally, so the system resolves it by `ComponentName` from the `sessionService` attribute of the `android.voice_interaction` resource — which is why it never appears in `cmd package dump`'s Service Resolver Table and why its `<service>` block carries only `android:exported="true"` (never `android:isolatedProcess`, see the per-process resolution gotcha above).
- **A session stretches its content view over the whole window it owns**: `VoiceInteractionManagerServiceImpl.showSessionLocked()` hands `onCreateContentView()`'s view to the window, so anything painted at the view's root covers every pixel of the `TYPE_VOICE_INTERACTION` window and hides whatever the device is showing - the user-visible symptom is "something renders but it's fullscreen". The root must stay unpainted and act only as an alignment stage: `stage.setGravity(...)` then `stage.addView(card(...))`, with the card the only element carrying a background. Positioning it is `android.ui.Gravity`'s bits, and **the whole `android.ui` package is unreachable from this Kotlin toolchain** ("Unresolved reference 'ui'" for `android.ui.Gravity.BOTTOM`), while `LinearLayout.setGravity(Int)` itself resolves - so the bits are spelled out literally (`private const val BOTTOM_CENTER_GRAVITY = 0x2 or 0x20`, BOTTOM | MIDDLE, which centres horizontally; TOP=0x0, CENTER=0x1, START=0x10, END=0x40).
- **The app-level wake overlay may carry no hit test outside its card**: `MainActivity` draws `WakeOverlay` *after* `MainNavigation` inside the same `Surface`, so that Compose layer covers the whole app surface - an invisible click-off region above the card (`Box(Modifier.fillMaxSize()).clickable(onClick = closeChat)`) sits on top of every screen and swallows every tap the user makes in the app (chat, settings and navigation all stop registering). Push the card down with a non-interactive spacer (`Box(modifier = Modifier.fillMaxWidth().weight(1f)) {}`) and put the close action on a real tap target inside the card (the 44 dp header mic). `Modifier.onClick` does not exist - the clickable API is `fun Modifier.clickable(enabled, onClickLabel, role, interactionSource, onClick)`, and `import androidx.compose.foundation` alone is rejected ("Packages cannot be imported"), so import the symbol `androidx.compose.foundation.clickable`.
- **Raise the session when the phrase is heard, not when the reply is ready**: the window is the user's only signal that an exchange is open outside the app, so `WakeChatService.requestSession()` is called twice per exchange - `SESSION_STATE_LISTENING` immediately after `playWakeCue()` and before the request is recorded, then `SESSION_STATE_REPLY` with the request and reply text. The exchange state travels in the bundle under a `state` string key alongside `request`/`reply` (the two halves never share memory), and a session must render an exchange that has no text yet ("Heard it - go ahead, I'm listening"). Unverified on device: whether the platform stacks or replaces the window across two `showSession()` calls in one exchange - the only teardown we control is `onDestroy()`/`finish()`.
- **A session's window is `(0,0)(fillxfill)`, i.e. the whole screen, and a `LinearLayout` measures to its content**: `dumpsys window windows` on the tab shows the `VoiceInteractionSession` window as `mAttrs={(0,0)(fillxfill) … ty=VOICE_INTERACTION fmt=TRANSPARENT}` with `frame=[0,0][2944,1840]`, so the window is full-screen and transparent. The stage inside it is not: with no forced size it measures exactly to the card, which is why `setGravity` is a no-op and the card paints in the window's **top-left corner** (confirmed by a `screencap` pixel scan: a solid `(43,43,43)` panel starting at x=0,y=0). Force the stage to fill the window with `stage.setMinimumWidth(STAGE_MINIMUM)` / `setMinimumHeight(STAGE_MINIMUM)` (a value far beyond any display, expecting the measure pass to clamp it to the space the window offers) so gravity can bottom-centre the card. Nothing else can fill the stage in this toolchain: `LinearLayout.setFillDimensions` is "Unresolved reference", the whole `android.widget.internal` package (which holds a `Filler` spacer) is unreachable, and no display-size accessor resolves (`android.graphics.DisplayMetrics`, `android.graphics.DisplayConfig`, `android.graphics.DisplayConfigManager`, `View.getDisplayMetrics(DisplayMetrics)` all report "Unresolved reference").
- **A `VoiceInteractionSession` builds its content view once and reuses it**: the framework creates the view the first time a session is shown and hands that same object to its window on every later `showSession()`, so an exchange that builds fresh views per show never changes on screen - the reply is never drawn and only the first card is ever visible (the user's symptom: "only 'Heard it - go ahead, im listening' renders, it never updates"). The views must be session fields constructed once and only ever **mutated** by an idempotent `paint()` driven from BOTH `onPrepareShow` (AOSP calls it before `onCreateContentView`, so it is the only place the bundle text can be captured) and `onCreateContentView` (which is the only guaranteed entry point, and painting again after wiring is what makes the first exchange show). Because the structure cannot grow, text is wrapped into a fixed pool of line `TextView`s (`MAX_LINES` × `LINE_CHARS`) - a legacy `TextView` never wraps. Empty `TextView`s measure nothing and `0x00000000` backgrounds paint nothing, which is how a state that shows no turn contributes no height and no ink.
- **Closing an exchange has to be sent to the session**: the session runs in another process and only sees the bundles it is handed, so a window the app never told it about staying open keeps its card on the home screen forever ("it never seems to close"). Send a dedicated `SESSION_STATE_CLOSE` bundle from the one place that ends an exchange, and in the session answer it by painting nothing plus `finish()` in `override fun onShow(args: android.os.Bundle?, showFlags: Int)` (painting nothing is the belt-and-braces: if `finish()` only hides the window, the card is invisible anyway). `onShow(Bundle?, Int)`, `finish()` and `hide()` all override cleanly; `onPrepareShow` takes a **non**-nullable `android.os.Bundle`.
- **`companion object Constants` members are not instance members**: `WakeChatService`'s state flows, `touchChat()`, `closeChat()` and `buildIntent()` live in `companion object Constants { … }`, so the UI can call them as `WakeChatService.closeChat()`, but a function defined on the class itself (e.g. one that calls `showSession()`) is **not** reachable from inside that block ("Unresolved reference 'requestSession'") and is not reachable as `WakeChatService.endExchange()` from a ViewModel either. Cross-process work belongs on the instance; the app reaches it through the service's own intent (`ACTION_CLOSE_CHAT` → `onStartCommand` → `endExchange()`), which is why the ViewModel's `closeChat()` sends that intent instead of calling the companion's reset directly.
